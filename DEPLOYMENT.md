# Deploying the demo sites

## step-a11y — CONFIRMED 2026-08-17, corrects the section below

The naming reads backwards from what you'd guess, and the "no separate
service for step-a11y" claim two paragraphs down is wrong — both were checked
directly after two pushes to `main` silently didn't show up live:

- `step-shoe-store-production.up.railway.app` (**no** "clean") is the
  **accessible twin** — `sites/step-a11y`'s build output. Confirmed by
  `curl`ing it: it serves `u1-implementation.js` with the
  `GENERATED by sites/step-a11y/build.mjs` banner.
- `step-shoe-store-clean-production.up.railway.app` (**with** "clean") is the
  untouched original — `sites/step-plain`. Confirmed: no `u1-*` anything in
  its HTML, `u1-implementation.js` 404s.

So a Railway project/service named **`step-shoe-store`** (not
`step-shoe-store-clean`) does exist, and it's the one that matters for
demoing the U1 implementation.

**It deploys the same way as step-plain below — manual `railway up` only, no
GitHub auto-deploy.** Proved by pushing two separate commits straight to
`main` (a mapping update, then a demo class-removal) and checking the live
file after each: neither showed up. The service's own Deployments tab
confirms it too — every entry reads `railway up ... via CLI`, none
`via GitHub`.

The good news: `sites/step-a11y` is **already linked** on this machine — `cd`
there and `railway status` shows it pointed at the right project/service/env
without needing `railway link` first.

```bash
cd sites/step-a11y
railway up                     # already linked here; no --service flag needed
```

Confirm it landed:

```bash
curl -s https://step-shoe-store-production.up.railway.app/u1-implementation.js | head -12
# visualFocus color / __u1Patch build string should match your local
# sites/step-a11y/public/u1-implementation.js, not a stale one
```

`railway up` uploads whatever is in the current directory as the build
context — same rule as step-plain below: run it from `sites/step-a11y`
itself, not the repo root.

## The auto-deploy problem

The `step-shoe-store-clean` Railway project (service `step-shoe-store-clean`,
domain `step-shoe-store-clean-production.up.railway.app`) runs the code in
`sites/step-plain`. It is **not wired to auto-deploy on push** — pushing to
`main` on GitHub does nothing here. Discovered 2026-08-15: the service's only
deployment was from 2026-08-13, two days and several pushes stale, with zero
new builds triggered in between.

Until that's fixed on the Railway side (Settings → the service → check the
Source/GitHub connection — as of this writing there may not be one at all),
**every change to `sites/step-plain` needs a manual deploy.**

## How to deploy step-plain manually

```bash
railway login                 # once, opens a browser
cd sites/step-plain
railway link -p step-shoe-store-clean   # once per machine/session
railway up --service step-shoe-store-clean
```

Confirm it landed:

```bash
railway deployment list       # newest entry should be SUCCESS, just now
curl -sI https://step-shoe-store-clean-production.up.railway.app/i18n/i18n.js
# should be 200, not 404, once the i18n switcher work is deployed
```

`railway up` uploads whatever is in the current directory as the build
context, so it must be run from `sites/step-plain` itself (matching the
service's configured Root Directory) — running it from the repo root would
try to deploy the whole monorepo instead.
